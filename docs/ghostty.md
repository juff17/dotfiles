# Ghostty

My [Ghostty](https://ghostty.org) configuration, in [`modules/ghostty/home/.config/ghostty/`](../modules/ghostty/home/.config/ghostty/). Every new window opens as a layout:

```
┌────┬─────────────────────────────────────────┐
│work│ btop (CPU only)                          │
│hub●├──────────────┬──────────────────────────┤
│view│ viewer       │ [dir] 1:zsh 2:claude ✻   │ ← tmux tabs
│▲ 2 │ files·diff·dv│ claude / shell           │
│+new│ (Alt+V)      │                          │
└────┴──────────────┴──────────────────────────┘
```

- **Top:** btop, showing only its CPU box. If btop isn't installed, htop runs instead.
- **Bottom right:** a tmux session with its tab bar at the top. Ghostty's tab keys drive tmux tabs.
- **Left:** the viewer, hidden until you show it with `Alt+V`; a new window opens without it, so the tabs take the whole row. It opens in Files (the yazi file manager, which previews documents), in the active tab's folder. `Alt+V` again hides it, and it comes back as you left it. Each Claude start or resume in the window points Files at that Claude's folder: straight away if Files is running, even hidden, otherwise the next time you switch to it. Tab switches it to Diagrams, the diagram viewer (`dv`), which shows the diagrams Claude draws. A header row shows both modes; click one to switch.
- **Alt+D:** the diagrams of the tab you're looking at, in a framed window titled with the tab, about 85% of the window (Settings › Layout) and centered, with the window you were in drawn dimmed round it: in the workspace, the active tab; in the hub, the tab of the session open beside the list, or else of the selected card. A background agent has no tab, so it has no diagrams, and the hub says so. `Alt+D`, `Esc` or a click on the dimmed part closes it and puts you back where you were. It's a tmux window, not a popup like New agent: tmux drops the image passthrough `dv` draws with from a popup, so the dimmed part is a snapshot of the window's text taken as it opens.
- **Todo:** a mode of the left pane, after Diff. It shows every repo's open todos grouped by category (bug, feature, follow-up, docs, question, other), with the active tab's repo first in each group. An item can also have a type (research, decide, action, review or chore), shown in color beside its repo; `t` cycles it, or `ghostty-todo add --type`. The selected one opens under its row: who added it, from which tab and branch, and its note. `enter` goes back to the tab that added it, even in another Ghostty window. If that tab is gone, a second `enter` opens a new tab in the item's worktree running `claude --resume` on the session that added it. Items come from the `/todo` skill, which has Claude run `bin/ghostty-todo` (Claude adds them only when you ask), or from the pane. `a` takes a message in your own words and hands it to Claude (Haiku 5.5 at medium effort, unless Settings says otherwise), which writes the title, category, type (when the message makes it clear) and note, and files it under the repo it's about: the one it names, even loosely, or the one where Claude finds what it mentions by searching the git repos on the list and beside them read-only, whichever tab you typed it in. Errands, and anything no repo holds, go under none: the message shows under "filing" with a spinner until the item replaces it, or with the error if Claude couldn't file it. `shift+a` adds one by hand: a title, a category, then a note, with the step you're on shown on the right. `m` marks todos and `w` hands the marked ones, or the selected one, to agents: one Claude per todo, started the way New agent starts a task (`launch` in `hub/model.mjs`), with Opus, auto mode and medium effort unless Settings says otherwise. Before `enter` starts them, `t` picks a new tab (behind the one you're on) or the background, `b` its own worktree (from the main checkout, the default) or the branch the todo was added on (a todo added outside git runs in the folder the viewer has open, the active tab's, and gets that folder's choices: the row says how many go there; when that folder isn't in git either, `b` isn't offered), and `m` the model. The prompt is the todo's title and note, and asks Claude to mark it done with `ghostty-todo done` when finished. In its own worktree, which Claude names for the todo and ends with its id, Claude commits there and asks before merging into main, then asks again before removing the worktree; it does neither unasked. Settings › Todo › Before merging into main can make it never merge, leaving that to you. A handed-off todo shows `✻`, and its card says which agent has it; while the hub lists that agent, `enter` opens it in the hub beside the list, as the tray's Go does (`go` in `hub/tray.mjs`): a tab agent through a session of its own, so the workspace stays on its tab, and a background agent with `claude attach`. Done items stay under "done today" and are dropped after a week (Settings: Keep done items). The list is one file, `~/.local/state/ghostty-layout/todos.json` (`$XDG_STATE_HOME`), so every window shows the same list. An item added outside a git repo shows `none` as its repo.
- **Diff:** a mode of the left pane, beside Files. It shows the uncommitted changes of the repository your active tmux tab is in, against the last commit (staged, unstaged and new files): a summary of what changed, a row per file with its added and removed lines, and one file open in place under its row with its diff. It checks git every second, so it empties once you commit.
- **Ping:** when Claude finishes or asks for permission in a tab you're not on, that tab turns red. Claude sends no desktop notification; the Agents widget below shows it.
- **Alt+H:** the keys, in a popup over the workspace or the hub. Each feature (Anywhere, Tabs, Viewer pane, Diff, Diagrams, Todo, Hub, New agent) is a section down the left, with its keys on the right; it opens on Hub in the hub, Diagrams over the Alt+D window and Anywhere elsewhere. `/` filters every section at once. Keys that are easy to forget are peach. The keys come from one table, `viewer/help.mjs`, so change it along with the table below.
- **Rail:** a strip down the far left. **work** and **hub** switch the window between this workspace and the agent hub, the counts under them are the agents that need you (▲), are working (✻), are done (✓) and are idle (○), **+ new** starts an agent, **view** shows or hides the viewer (Alt+V; only in the workspace), **? help** shows the keys (Alt+H), and **⚙ set** opens Settings (Alt+S). The hub button gets an orange dot while anything needs you. A tab running Claude carries the same glyph in the tab bar.

## Agent hub

The hub is the window's second view (`Ctrl+Shift+A` or the rail's **hub**). It shows every Claude session on the machine, from every Ghostty window and the background (`claude --bg`):

- **Lanes** for task agents: **Needs you** (a permission prompt, a question, or a monitor that raised something), **Working** (with the command running now and for how long), **Done** (finished, and you haven't looked yet) and **Idle**. A lane that fills up keeps going: Needs you scrolls with a "▾ more" cue and never shrinks a card, Working drops to cards that show only the command, Done keeps its newest two as cards (Settings: Done cards before folding) and folds the rest to a line each, and Idle is a line each; Settings' Show the Idle lane turns it off, giving its room to the other three. An empty lane says so (*Nothing needs you*, *Nothing working*, …). A tab that parked its conversation in a background job is one card with that job: its state comes from the job, and Enter and `o` go to the tab.
- **Monitors** in a tray below, which keeps room for five even when fewer run (Settings: Rows kept for monitors) and grows to about a third of the screen when more do: each Monitor a session armed (pr-babysit's `watch_pr.py`, logger's `watch_logs.py`, or any other), with what it watches, its latest event and when it came. A monitor is *watching*, *needs action* (its last event was a failed, manual, stuck or conflicted job, an error, a crash, or an auth, setup or blocked problem, and you haven't seen it; Settings: Count as needing you), *stale* (its command no longer runs) or *ended* (it expired, failed, or went with its session's last process when the session was resumed; it leaves after five minutes (Settings: Ended monitors leave after)). One you stop, with `x` or by asking its agent, leaves at once. A session that's watching something stays in the strip; it shows in a lane only when it needs you. `x` on a monitor stops just that one: the hub ends the monitor's own process group, so the session and its other monitors keep running. Answering `a` to its question stops it without asking from then on, by turning off Settings' **Ask before stopping a monitor**; turn it back on there to be asked again.
- **Open a session:** Enter opens the agent's live session beside a list of the rest, and your keys go to it. A tab agent opens through its own grouped tmux session, so the workspace stays on the tab it was on; a background agent opens with `claude attach`. `Ctrl+Shift+B` closes it and goes back to the board. In the list beside it, `x` or `Ctrl+X` closes the selected agent (or stops the selected monitor), asking first, as on the board. Switching tabs in it, from its tab bar or with the tab keys, switches only what that pane shows, and the list follows to the agent in the new tab.
- **Hub tabs:** the open session's tab bar has the tabs opened from the hub, plus the workspace tabs running Claude. A tab you open there (`Ctrl+Shift+T`), or that New agent opens, is a hub tab: it shows in the hub and not in the workspace, and its card says *hub tab*. A workspace tab joins the hub's tab bar within a second of Claude starting in it, and leaves a few seconds after Claude exits, once the hub isn't showing it; a plain shell, like the tab the window opened with, never shows there. A tab is still one tab in both places, so closing a workspace tab from the hub closes it in the workspace.
- **New agent** (`n`, or **+ new**): a task with a first prompt, run in a new hub tab or in the background, in its own worktree (the default; Claude makes it first with EnterWorktree and names it for the task, led by the ticket key when the task gives one) or on the current branch; a PR babysitter (`/pr-babysit <link>`, in the background); or a log watcher (`/logger watch <source>`, in the background). Folder, model, permission mode and effort are fields of their own, starting at Opus, auto, medium for a task and Sonnet, auto, medium for a monitor; recent folders are one keypress away (up to eight; Settings: Recent folders shown). They're ranked by z.sh's frecency from `~/.z` (`$_Z_DATA`), merged with the folders agents ran in, the folder you last started one in staying first; without `~/.z`, or with Settings' Rank folders by at last used, newest first. With Only git repos (the default) a subfolder or worktree counts as its repo and folders outside git are left out. Folder starts on the selected agent's repo, else the newest recent, unless Settings' Default folder says `~/projects`.
- A done agent counts as seen once you open it, mark it (`e`), or its tab is the one in front.

The hub needs no Claude Code hooks. It reads what Claude already writes: each running session's `~/.claude/sessions/<pid>.json` (its status, what it's waiting for, its tmux pane) and its transcript (the prompt, the tool running, the last reply, the context used, and every Monitor with the events it delivered).

The theme is Catppuccin Mocha.

## Agents widget

A Plasma panel widget puts the hub's agents beside the clock. It is the only alert: Claude sends no desktop pop-ups (the claude module has no notification hook, and Ghostty's `desktop-notifications` is off):

- **In the panel:** a glyph and count per kind: ▲ needs you, ✗ broke (a monitor saw a failed job, an error, a crash or a conflict), ✻ working, ◉ watching (◌ gone quiet) and ✓ done; ○ when nothing runs. Settings › Tray › Count picks which kinds it counts. A new ▲ or ✗ fills it with its colour for two seconds (Settings › Tray; 0 turns it off), and a ring stays around it until you open the inbox (Ring until the inbox opens). Settings › Tray can also pop up a KDE notification (`notify-send`) and play a freedesktop sound (`canberra-gtk-play`, else `paplay`), or a sound file of yours (Sound › custom file, then its path under Sound file), for a new ▲ or ✗, the sound only while Ghostty isn't the window in front unless you turn Quiet while Ghostty is focused off.
- **The inbox** (click it, or the shortcut you give it; its width and most height are in Settings › Tray): every item in those sections, needs-you first, each with its buttons. **Allow** and **Deny** answer a permission prompt, only while it's on screen, as in the hub; **Go** opens the agent's live session in the hub, beside the list of the rest, and brings Ghostty to the front (the workspace stays on its tab); **Open hub ↗** shows the hub. Keys: `j` / `k` move, `↵` presses the first button, `1` / `2` / `3` the first three, `x` dismisses an item until it changes (on a babysit proposal it rejects it), `esc` closes. Done items fold into one line until shown, unless Settings › Tray says not to, and leave once you open them.
- **Notes:** a session can post something only it knows needs you, a fix ready to push or a finished rebase, as a ▲ item: pr-babysit's `notify.sh` writes it to `$XDG_RUNTIME_DIR/agent-hub/notes/`. Go takes you to that session; Go or `x` clears it, and it's dropped after a day.
- **Babysit proposals:** anything a babysitter wants to do under your name (post a reply, push its commits, retry a flaky job, run a manual job, approve a deployment, move its commits after someone pushed) waits as a row with its own buttons: a reply shows the text it would post with **Post**, **Edit** and **Skip**; a push **Push**, **Review** and **Go**; a manual job **Run** and **Skip**; a flaky job, under ✗ broke, **Retry** and **Go**. Edit and Review open the proposal in the Alt+A popup. A proposal that failed when it ran stays as a ✗ row to **Try again**, Go to, or dismiss. With Settings › Approvals › Also show buttons in the tray off, a row only opens Alt+A or the session. See [Approvals](#approvals).
- It reads and acts through `ghostty-hub tray` (`hub/tray.mjs`), the same agents the hub shows, so handling an item in one clears it in the other. It keeps agentd running while it's in the panel.

## Approvals

A PR babysitter (`/pr-babysit`) never sends anything under your name itself. It proposes, a script runs exactly what it proposed once you approve, and anything that goes wrong goes back to the babysitter:

1. **The agent proposes.** `approval.py propose` (in the skill's `scripts/`) writes one JSON file to `$XDG_RUNTIME_DIR/agent-hub/approvals/` with the whole action: the reply's text and the thread it answers; the commits, the lease and the branch for a push; the job for a retry or a manual job. The tray and Alt+A show it at once.
2. **You approve** in the tray or Alt+A, after editing a reply if you like, or dropping commits from a push.
3. **`approval.py approve` runs it.** One `gh api` / `glab api` POST for a reply, a retry, a manual job or a deployment; for a push, a check that the worktree is still where it was proposed and that the remote branch is still at the lease (`git ls-remote`), then `git push --force-with-lease`. The tray runs it under `zsh`, so the tokens from `~/.zshenv` are there even though the panel didn't load your shell. What happened is written back into the file.
4. **The babysitter hears about it.** `watch_pr.py` checks the folder every two seconds between polls and prints an `[approval]` event for each settled proposal of its session: approved (with the reply as you edited it, if you did), rejected, failed and why, or handed back. Dropping commits from a push, and moving commits onto a head someone else pushed, are always handed back: the babysitter rebuilds the branch, reruns lint and tests, and proposes again. A failure stays in the tray as a ✗ row until it's tried again, proposed again or dismissed.

Nothing is approved that you weren't shown. The tray offers Post only for a reply short enough for its preview, and Push only for a push that takes nothing off the branch; anything else opens in Alt+A first. Alt+A keeps a reply's line breaks, lists the commits a force push would take off the remote, and scrolls (`J` / `K`) what doesn't fit, refusing `a` until all of it has been on screen; if the proposal you were reading is replaced or settled elsewhere, the next `a` only says so. `approve` checks again before it runs: a push that the worktree, the lease or the commits it removes no longer match is refused; a job whose commit is no longer the PR's head isn't run; a deployment approves only the environments it named, and only while all of them still wait. A proposal being approved can't be replaced or dismissed until it's done. Retries run on their own at most once per job name on a PR, since each retry gets a new job id, and never for a job whose real name or stage (looked up from GitHub or GitLab) says deploy, release or prod.

Settings › Approvals says which kinds run without asking: a retry (once per job), moving commits after a push, a GitLab manual job (never one whose name or stage says deploy, release or prod), a push, and replies (off, drafted for approval, or posted). A GitHub deployment or workflow approval always asks. Something run on its own still shows in the babysitter's briefing, marked auto. PR babysit's own section adds what the babysitter may do in the worktree: auto-fix review comments, auto rebase (off, when clean, always) and tray notes for finished stages; `watch_pr.py` prints them as a `[settings]` event whenever they change.

## Install

`./install.sh ghostty` sets it all up: `ghostty`, `tmux` and `btop` from the module's `packages.txt`, yazi from its `install.sh` (snap), and Node.js for Diff and Diagrams from the `node` module (fnm), which it requires. btop and yazi are optional, see above.

`./install.sh --links ghostty` symlinks each file in `modules/ghostty/home/.config/ghostty/` into `~/.config/ghostty/`, so edits here apply live. A file already in the way is moved to `.dotfiles-backup/`. Windows that are open during install keep their layout (the module's `after-link.sh` records them); new windows get the new one.

The Claude Code hooks live in the claude module's `modules/claude/config/core/settings.json`:
- **SessionStart:** `bin/ghostty-claude-start` points the viewer at Claude's folder.
- **Stop** and the `permission_prompt` notification: `bin/ghostty-claude-ping` rings the tab's bell, unless Settings › Tray › Tab bell is off.

Diagrams come from the claude module's diagram-pane mod (`modules/claude/mods/general/diagram-pane`), which renders each one to a PNG and writes each session's tabs to a file for its tmux pane, under `~/.cache/claude-diagram-pane/panes/`. `dv` shows the file of the window's active tab (or, in the Alt+D window, of the tab it was opened for), and closes a diagram by rewriting it; the format is in the mod's README. A new Claude session starts with no diagrams, and a resumed one gets its own back.

## How it works

Each window is one Ghostty split running two tmux servers, one inside the other:

- **The outer tmux** (`layout.conf`, socket `ghostty-layout`) lays the window out. It runs one session per window, with no status bar and no prefix key. Its panes are btop, the viewer and the tab session.
- **The tab session** (`tmux.conf`, socket `ghostty`) runs in the outer tmux's bottom-right pane and keeps your tabs. `prefix` keys reach it untouched, because the outer tmux has no prefix.
- **The hub's tab session** (`hubtabs-<window>`, on the same server) is a detached session that `hub_tabs` in `ghostty-lib.sh` makes the first time the hub opens a tab or a session. It has the hub tabs, which only it has, plus the workspace tabs running Claude, linked in (`link-window`): `hub_tabs` links the ones running Claude when it makes the session, and the tab a session opens on, and `agentd` links a tab once Claude starts in it and unlinks it once Claude has been gone a few seconds (`hubLinkArgs` in `hub/daemon.mjs`), but not while an open session shows it. With no tabs left it ends, and the next tab or session the hub opens makes it again. The session the hub opens is grouped with it rather than with the workspace's session, so a tab opened there lands here. It goes when the window closes.

Ghostty's own splits can't do this layout. Its D-Bus actions can open splits but not size them, and a `global:` keybind acts on every split of every window, so a script can't resize one split without moving the others. tmux sizes panes exactly, in one step.

The scripts in `bin/`:

- **`ghostty-surface`** is Ghostty's `command`, so it runs in every new split. In the first split of a new window, it builds that window's outer session at the window's size, then attaches to it. Any other split gets your shell. It also runs the outer panes: `ghostty-surface top` runs btop and `ghostty-surface tabs` runs the tab session. A new window has no viewer: `ghostty-viewer-toggle` adds it.
- **Keeping btop's height:** tmux shares a window resize out between the panes, so a `window-resized` hook puts btop back to its height (Settings › Layout, or `GHOSTTY_TOP_ROWS`) after one. That includes the resize on attach, when KDE maximizes a new window while its layout is being built.
- **`ghostty-viewer-toggle`** runs on `Alt+V`. Hiding moves the viewer's pane to a window of its own, `viewer`, which is never shown (`break-pane`), so yazi and dv keep running, with passthrough off so nothing they draw then reaches the screen; showing moves it back left of the tab session (`join-pane`, at Settings › Layout's width) and focuses it. With no viewer yet, or after `q` in dv closed it, it opens one (`open_viewer` in `ghostty-lib.sh`), which holds focus while yazi asks the terminal its questions, since tmux hands the answers to the focused pane.
- **Keeping the viewer's share:** Ghostty opens a window small (around 83×28) and KDE grows it after, so a split made at the small size ends up far from its share once tmux shares the growth out. `open_viewer` adds a second `window-resized` hook that sets the viewer back, hidden or shown, to its percent of the row (Settings › Layout › Viewer pane width, 30 by default, or `GHOSTTY_VIEWER_SHARE`) after every resize.
- **`ghostty-claude-start`** sends the viewer's yazi to Claude's folder with `ya emit-to` (yazi runs with a client id per window), and leaves the folder in a file that Files reads when it next starts. It never opens the viewer or moves focus. It also saves where Node.js is, which Diff, Todo and Diagrams need and Ghostty's own PATH lacks. The viewer gets `DV_TABS` so Diagrams, Diff and Todo know which tab session to follow; `tmux.conf` touches `$XDG_RUNTIME_DIR/ghostty-layout/tab-changed` when the active tab changes, so they switch with it.
- **`ghostty-viewer`** runs the left pane's modes in turn: `yazi` (Files), `viewer/diff-view.mjs` (Diff), `viewer/todo-view.mjs` (Todo), `dv` (`viewer/diagram-view.mjs`, Diagrams) and any you added in Settings › Workspace, which run their command with `bash -c` in the folder Files was in. Which are on, their order and the one it opens in come from `viewer/modes.mjs`, read again at each switch, so a change shows the next time the mode changes. It tells each mode the names of the modes that are on (`GV_MODES`, tab-separated), which one it is (`GV_AT`) and where `q` goes (`GV_QUIT`); a mode exits with 10 + a mode's number to switch to it. `yazi` can't choose an exit code, so it says where to go by whether it writes its `--cwd-file`: Tab and a click on a mode's tab do, `q` doesn't, and a click leaves the mode's number in the file `GV_NEXT_MARK` names first. An added mode goes to Files when its command exits, and waits for a key first when it fails, so a broken command can't spin. `yazi/init.lua` and `yazi/theme.toml` lay yazi out like the design: the mode header, a file list beside a wide preview, and a short status bar. `dv` draws images through tmux with kitty Unicode placeholders, so panning moves in whole cells.
- **`ghostty-todo`** is the todo list's command line: `add`, `file`, `list`, `done`, `undo`, `edit` and `rm` (`ghostty-todo help`). `file` adds the message as a filing item and runs `claude -p` with the filing model and effort from Settings (Haiku 5.5, medium) in the item's folder, sending `/todo` with the item's id, where it was typed and the message, so the todo skill (`modules/claude/skills/general/todo`, its Filing section) does the filing, as `/pr-babysit` and `/logger` do theirs. It runs in `dontAsk` mode with only the read-only search, `ghostty-todo add` and `ghostty-todo repos` allowed, and no other skill. Claude picks the repo, as the skill always does (`ghostty-todo repos` lists the candidates: the repos on the list and the git repos beside them), writes the item and runs `add --filing <id>`, which replaces the filing item with it, with no tab or session. If Claude exits without doing that, or runs past the time limit in Settings (3 minutes), `file` records the error on the filing item. Todo runs `file` in its own process group, so closing the popup doesn't stop it, and dropping the item kills the group. `add` records the repo (the main checkout, so a worktree's items count as its repo's), the branch and worktree, the tab's tmux pane, and the Claude session it runs under, found from its parent processes. It records only the pane, since a window shows in the hub's sessions too; Todo looks up the window's own session when it goes there. `viewer/todo.mjs` holds the store both share. Each write takes a lock folder beside the file and replaces the file whole.
- **`ghostty-todo-panel`** opens `alt+t`'s popup on the client it's given, at the size in Settings › Layout, and runs itself inside it with `--panel`. It reads the window from the client's session, so the list follows that window's tab session, and runs `viewer/todo-view.mjs` with `TD_POPUP=1`: no mode header, and keys that close the popup instead of switching modes. Inside a popup tmux's own bindings don't apply, so the list itself reads `alt+t` as close.
- **Settings** (`viewer/settings-view.mjs`, in a popup from `bin/ghostty-settings`) changes values the hub, the tray, Todo and pr-babysit's watcher used to have built in, in sections: New agent, PR babysit, Approvals, Log watcher, Todo, Hub & monitors, Tray, Editor, Workspace, Layout, Viewers and Keybinds. A setting can show in two sections under a name for each (PR babysit's Auto push changes is Approvals' Push fixes to the PR); Approvals' Popup key is Keybinds' Approvals popup; a few rows only show a value set elsewhere (the Meta+A key). Workspace's viewer modes are one setting, `workspace.modes`, a list of `{ id, on }` with a `name` and `cmd` for one you added (its id starts `x-`); a built-in mode the list lacks comes back at its end, and at least one stays on. Its other rows: whether new windows open with the viewer shown, which mode it opens in, and whether Alt+T and Alt+D still open while Todo or Diagrams is off. Each change is saved as it's made to `~/.local/state/agent-hub/settings.json` (`$XDG_STATE_HOME`), which holds only what differs from the defaults, as flat `key: value` pairs. A changed setting shows a peach dot and its default under it. `hub/settings.mjs` lists every setting with its default and range. A value that's missing, broken or out of range reads as its default. The "don't ask again" for stopping a monitor, which the hub used to keep in `prefs.json`, carries over.
- **Keybinds** (Settings › Keybinds, `hub/keybinds.mjs`) moves the keys that work anywhere in the window. The alt keys (Help, Todo, Settings, Diagrams, Approvals, the viewer, New agent, the editor) can take another alt and a letter or digit; Ghostty's (Workspace ↔ hub, Back to the board, New tab, Close tab, New window) another ctrl+shift and a letter or digit. A key another row has, or one the shell, Claude Code or Ghostty's own defaults use, is refused and not saved. `layout.conf` stays where each alt key's command is written: `bin/ghostty-keys` copies the `bind -n M-…` statement to the new key in `~/.local/state/agent-hub/keys.tmux.conf` and sources it into the layout's tmux, which also runs it as `layout.conf` loads. Ghostty's moved keys go in `~/.config/ghostty/keys.local.ghostty`, which `config.ghostty` includes, and Ghostty reloads its config on SIGUSR2. Alt+H shows the moved keys, and Settings and Help close on theirs; the Todo popup still closes on `alt+t`, `esc` or `q`.
- **Your instructions** (`hub/prompts.mjs`) for a task from New agent and a todo handed off with `w`: a Markdown file each in `prompts/` beside `hub/`, in this repo (`prompts/task.md`, `prompts/todo-handoff.md`). Git ignores them: the repo keeps `<name>.md.example`, and install (`after-link.sh`, through `copy_prompt_examples` in `bin/ghostty-lib.sh`) copies each to its `.md` once, never over one you have, like a `.env.example`. Edit the `.md` to change them; Settings shows each one's path and how many lines it has, under Task in New agent and under Hand-off in Todo. They're sent after the prompt the code builds, joined into one line, as a tab agent's command is typed into a shell. HTML comments in a file are left out. Filing a todo has none: it runs the todo skill, which you change instead.
- **`ghostty-help`** opens Alt+H's popup on the client it's given (`display-popup -c`), for `layout.conf`'s binding and the rail's button alike, and runs itself inside it with `--panel` to start `viewer/help-view.mjs`. The window name it's passed (`work`, `hub`, `diagrams`) picks the section the list opens on. The rail finds its window's client with `list-clients`, since a click doesn't say which client made it. Inside the popup, the list reads `alt+h` as close.
- **`ghostty-diagrams`** opens the Alt+D window: a `diagrams` window in the outer session running `dv` with `DV_FRAME` (the frame and title) and either `DV_TABS` (a tab session to follow: the workspace's, or the `peek-<pane>` session of the hub's open session) or `DV_PANE` (one tab pane: the selected card's), and `DV_UNDER`, the window it was opened from, which `dv` captures and draws dimmed round the frame (`viewer/backdrop.mjs`). `layout.conf` runs it from the workspace, hands the hub a key of its own in the hub (`hub.mjs` `DIAGRAMS_KEY`), and passes `Alt+D` through to `dv` in the diagrams window, which closes. `agentd` treats the diagrams window like the hub: the tab behind it isn't being looked at.
- **`ghostty-editor`** runs on `alt+e`. It reads the active pane's folder from the tab session `layout.conf` names (the window's, or the hub's open `peek-<pane number>`) and opens `git rev-parse --show-toplevel` of it (or the folder itself, if Settings › Editor says so) with the editor's command from Settings › Editor, passing `-n` for a new window or `-r` to reuse one (`-a` for Sublime Text).
- **Tab keys:** Ghostty sends them as escape codes, and the outer tmux runs the matching command in the tab session, whichever pane has focus; in a session the hub opened, they act on that pane's own session (`peek-<pane number>`) instead, so a new tab there is a hub tab. `Ctrl+Shift+A` is one of them too, and switches the outer session's window.
- **The hub's windows:** `add_hub` in `ghostty-lib.sh` gives each outer session a second window, `hub`, and a rail (`hub/rail.mjs`) down the left of both. Clicks on a rail pass through to it without selecting its pane, and it never keeps focus, like btop. It puts its own width back after a resize. `ghostty-hub setup` adds the rail and the hub to a window opened before they existed.
- **`hub/agentd.mjs`** is the one process that watches the sessions, so every rail and hub together cost one. Once a second it reads the session files, the new lines of each transcript and the tab server's panes, writes `$XDG_RUNTIME_DIR/agent-hub/state.json`, sets each Claude tab's `@agent` glyph, which `tmux.conf` draws, and keeps each hub tab session to the workspace tabs running Claude. The hub and the rails start it when it isn't running and register in `clients/`; it exits a little after the last of them. `hub/model.mjs` holds the logic that turns a session into a card, and `hub/hub.mjs` and `hub/rail.mjs` draw.

New windows are told apart from splits you open yourself by their D-Bus window number, recorded in `$XDG_RUNTIME_DIR/ghostty-layout/<ghostty pid>/known`.

Settings you can change through the environment:
- `GHOSTTY_TOP_ROWS` (default: Settings › Layout › btop height, 10): rows for btop; set, it wins over Settings.
- `GHOSTTY_VIEWER_SHARE` (default: Settings › Layout › Viewer pane width, 30): the viewer's percent of the bottom row; set, it wins over Settings.
- `GHOSTTY_RAIL` (default 1): `0` leaves out the rail and the hub.
- `GHOSTTY_RAIL_COLS` (default: Settings › Layout › Rail width, 6): the rail's width; set, it wins over Settings.

### The Agents widget

`./install.sh --links ghostty` links the widget's folder, `modules/ghostty/plasmoid/dev.dotfiles.agents/`, to `~/.local/share/plasma/plasmoids/dev.dotfiles.agents` as one link (the module's `after-link.sh`). It isn't under `home/` because Plasma refuses a widget whose files are links that lead outside its folder. Check that Plasma sees it:

```bash
kpackagetool6 --type Plasma/Applet --show dev.dotfiles.agents
```

Then put it in the panel, once:

1. Right-click an empty part of the panel and choose **Add Widgets…**. A sidebar of widgets opens.
2. Type **Agents** in its search box.
3. Drag the **Agents** card onto the panel, left of the system tray, and let go. It shows as a small dark chip: `✻2` with two agents working, `○` with none.
4. Give it its shortcut: right-click the chip, **Configure Agents…**, **Keyboard Shortcuts**, set **Meta+A** (the inbox's header names it). Set it there rather than over D-Bus, which can crash KWin.

Plasma loads the widget's files when its panel starts, so after changing them, or if Agents isn't in the widget list yet, restart the panel: `systemctl --user restart plasma-plasmashell` (windows stay open).

If the chip shows **"Sorry! There was an error loading dev.dotfiles.agents … package does not exist"**, the folder isn't one link: `ls -la ~/.local/share/plasma/plasmoids/` should show `dev.dotfiles.agents -> …/modules/ghostty/plasmoid/dev.dotfiles.agents`. Run `./install.sh --links ghostty` to fix it, then restart the panel as above.

## Tests

Each UI keeps its decisions (keys, cursor and selection, prompts, layout, parsing) in a module that does nothing on import. The file that runs keeps only the drawing and the tmux and process calls. That way the decisions have tests beside them:

- **Agent hub:**
  - its model: transcripts, monitor events, lanes, fitting a full lane, and the commands a new agent runs.
  - `agentd`'s scanning (`daemon.mjs`): sessions, transcripts read as they grow, tmux panes and which tab is being looked at, tab glyphs, which workspace tabs the hub links in, whether monitors still run, the single-copy lock, and clients.
  - the board's keys, selection and layout (`keys.mjs`, `board.mjs`), and prefs and recents (`prefs.mjs`).
  - the New agent form, the rail, and the state client.
- **Agents widget:** its items (sections, what's new, dismissing), babysit proposals as rows with their buttons, and running `approval.py` for them.
- **Approvals popup:** its keys: stepping through proposals, a push's commits, drops and diffs, editing a reply inline or in `$EDITOR`, and approving with "always" (`approvals.mjs`). `approval.py` itself is tested with the `claude` module (`tests/test_pr_babysit_approval.py`), against a fake `gh` and a real bare repo.
- **Viewers:**
  - `dv`'s zoom and pan math.
  - Todo: the store, and the view's keys, cursor, prompts, edit form and hand-off (`todo-ui.mjs`).
  - Diff: git parsing, the file list and keys (`diff.mjs`).
  - Diagrams: pane files, tabs and keys (`diagram.mjs`).
  - Help: the filter and the overlay (`help-nav.mjs`).
  - The backdrop and the kitty graphics helpers.

Drawing, and anything that needs a live tmux server, has no tests. The tests use only Node's built-in test runner:

```bash
./test.sh ghostty
```

That runs every `*.test.mjs` under `viewer/` and `hub/`, so a new test file is picked up on its own. CI runs these and the `claude` module's tests on every push to main and every PR (`.github/workflows/tests.yml`).

## Limits

- **btop's pane** only displays. It ignores the mouse and never takes focus, so keys always go to the viewer or the tabs. If btop exits anyway, it starts again a second later.
- **Dividers:** the line under btop can't be dragged, so a drag that runs up over it doesn't resize btop. The divider beside the viewer still drags, until the window next resizes and the viewer goes back to its share. The hub's list beside an open session can't be dragged either, and puts its width back after a window resize.
- **Right-click** goes to the program under the pointer; tmux's own pane menu is turned off.
- **The first `Alt+V`** in a window starts yazi, which takes about a second to be ready. The viewer has focus throughout: yazi asks Ghostty about the terminal through tmux, and tmux gives the answers to whichever pane has focus; in Claude's pane one of them would read as Alt+P and open the model picker. Hiding and showing it after that is instant, as yazi keeps running.
- **Closing the last tab** closes the window. Only workspace tabs count: closing the last one also closes the window's hub tabs and whatever runs in them.
- **Ghostty tabs:** tabs made from Ghostty's own tab button don't get the layout.
- **Answering from the hub** (`a` / `d`) works for tab agents, and only while the prompt is on screen. A background agent's prompt is answered in its session (Enter). The same goes for Allow and Deny in the Agents widget.
- **Edit and Review in the Agents widget** open Alt+A in the Ghostty window used last, which may not be the one in front.
- **Go in the Agents widget** brings the first Ghostty window to the front. With several layout windows open, the agent still opens in the right window's hub, but it may be another window that comes forward.
- **Sessions outside the layout** (Claude in another terminal or another tmux) show on the hub, but can't be opened from it.
- **An open session resizes its tab** to the hub's pane, the way two tmux clients on one window do; it goes back when you're in the workspace again.
- **`shift`+drag** selects across the whole window, btop and viewer included, since Ghostty sees one split.
